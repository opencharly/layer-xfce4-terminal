# 2026.242.1906 — fix(xfce4-terminal): advance stale pins so the candy gate is green again

## Summary

Two things: this repo's gate is red on `main`, and its `layer-sway-desktop` pin is a
version-skew source.

### 1. The gate fails on unmodified `main`

```
$ git checkout main && charly box validate
charly: error: command "validate": validation error:
  candy "github.com/opencharly/pod-dbus" depends: unknown candy "supervisord"
exit 1
```

**Root cause, not the symptom.** The pinned versions predate the move from BARE dependency
names to full `@github` refs, so their declared dependencies resolve to nothing outside a
project that happens to define those names. `pod-sway@v2026.235.2110` carries the old
`pod-dbus`; the newer `pod-sway` release pins `pod-dbus` properly.

### 2. The layer-sway-desktop pin drags old transitive pins

`layer-sway-desktop` fixed four such stale pins in opencharly/layer-sway-desktop#3.
`v2026.238.2103` predates that, so composing this candy pulls the old
`layer-xdg-portal` and `layer-chrome-sway` back in, which charly reports on every build of
such a project:

```
Warning: candy github.com/opencharly/layer-xdg-portal resolved to multiple versions;
using newest 2026.242.1655 (from …@v2026.242.1648), ignoring 2026.144.1443 (from …@v2026.237.557)
```

Two pins move:

```
pod-sway            v2026.235.2110 -> v2026.241.2004
layer-sway-desktop  v2026.238.2103 -> v2026.242.1839
```

No packages, services or plan steps change.

## How tested

Before, on unmodified `main`:

```
$ charly box validate
1 validation error
exit 1
```

After, on this branch:

```
$ charly box validate
exit 0
```

Bisected rather than guessed: bumping `layer-sway-desktop` alone left the gate at exit 1
with the `pod-dbus`/`supervisord` error, which identified `pod-sway` as the second stale
edge. Run with charly **`v2026.238.1242`**, the version this repo's `deploy.yml` clones and
builds, so it is the same gate CI runs. Exit codes read directly from `charly box validate`,
not through a pipeline.

The consuming project's zero-warning bed run lands with the repin that follows this tag: a
transitive pin only stops being resolved once the repo removing it is merged and tagged, so
no bed run in *this* repo can demonstrate the drop.
